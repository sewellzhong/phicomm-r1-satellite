# R1 原厂四麦与音频调校优先路线（2026-09-08）

## 决策与成功定义

用户决定将原厂音频处理链攻关提升为首台 R1 的最高开发优先级。项目允许为此使用拆机、Android root、临时或补丁 boot、定制 recovery/system、专用 SELinux 策略、特权系统服务和刷机；实现复杂或耗时不能作为降级理由。恢复门槛通过后，再继续播放中打断、流式回答、闹钟、免打扰、媒体等上层功能，避免建立在错误采集架构上返工。

成功不是“原厂文件仍存在”或“标准 AudioRecord 经过原厂 HAL”，而是卫星实际消费设备内原厂四麦、MicArray、DOA、AEC、DSP及校准链路产生的音频结果。目标架构保留卫星 APK 的普通应用权限，由专用特权代理调用设备自身的专有组件，并通过受保护的本地接口向 APK 提供固定格式音频。

当前标准 `VOICE_COMMUNICATION` AudioRecord 和已验证的应用层增益/降噪继续作为对照基线。只有本文列出的原厂路线全部留下可复现失败证据，且用户审阅证据后明确接受，才可将其升格为生产降级方案。

## 已知基础与限制

- 目标设备为 `r1-sample01`，固件 3448、Android 5.1.1/API 22、ARMv7。
- Audio HAL、`libuni4michal.so`、`libuni4michalchance.so`、AK7755 data2 固件和板级配置已与 3448 OTA 目标核对。
- 独立 APK 可以加载 `Uni4micHalJNI` 并读取 `UNI_4MIC_HAL_ANDROID_V1.1`，但其 `u:r:untrusted_app:s0` 域被拒绝搜索标记为 `audio_device` 的 `/dev/snd`，`openAudioIn(2)` 返回 0。
- Manifest 的 `RECORD_AUDIO` 只允许经 AudioRecord/AudioFlinger 录音，不授予直接 tinyalsa、mixer、I2C 或 DSP 控制权限。
- 当前标准链已通过 1 米固定短语可懂度、10 dB 分离子门槛和 30 分钟流式处理稳定性；这些证据不代表原厂阵列、AEC、DOA或播放中唤醒已经可用。
- 当前生效的 `com.phicomm.speaker.device/player` 是第三方修改覆盖层。原厂系统基础和专有库来源已核对，但不能把当前覆盖包的体验写成纯原厂效果。

## R0：完整备份与回刷门槛

> 2026-09-11现行边界：用户选择[免拆分级授权](2026-09-11-r1-no-disassembly-authorization.md)。
> R0仍为`pending`，但在当前首台和3448基线、较低权限路线有可复现实机不足证据、且目标
> 分区完成双读与写后读回门禁时，可依次推进必要的boot、system或recovery修改。Loader、
> 分区表、物理首4 MiB、擦除、格式化及整盘覆盖仍须另行授权。下列R0条目继续作为完整
> 恢复能力的独立门槛，不因功能授权放宽而改写。

除上述设备限定例外外，任何永久root、boot、SELinux或分区修改前必须完成以下门槛：

1. 重新确认设备 ID、硬件、固件 fingerprint、分区表、当前 APK/服务状态和现有恢复基线。
2. 通过设备实际可用的 Loader/Maskrom、recovery 或等价低层入口枚举所有 eMMC 区域；分区名称不预设，以设备读回结果为准。
3. 备份完整 eMMC 及枚举出的引导、参数、boot、recovery、system、data/config、原厂 APK、Audio HAL、四麦库、DSP固件和校准内容。涉及家庭凭据的 data/config 镜像只进入加密本地存储。
4. 为每个镜像记录设备、来源、偏移、长度、工具版本和 SHA-256；至少保存两份独立本地副本，并完成逐字节或哈希复读校验。
5. 验证低层恢复入口在 Android 无法启动时仍可进入，执行一次受控完整回刷；回刷后复核启动、ADB、Wi-Fi、蓝牙、麦克风、扬声器、按键、灯效和关键音频文件哈希。

门槛未通过时停止高风险修改并记录阻塞。`r1-sample01` 在门槛通过后已有用户授权继续 Root 和刷机实验；设备身份或固件变化时必须建立新的对应基线。

## R1：权限与执行环境

按以下顺序推进并为每一步保留命令、镜像哈希、启动结果和回退证据：

1. 优先尝试不写 eMMC 的临时启动或临时 root，以取得只读盘点和原厂接口验证能力。
2. 需要常驻时使用可回滚的补丁 boot，验证 `su -c id`、启动链和恢复入口，不把 Root 管理程序或公网 ADB 当作交付能力。
3. 保持 SELinux Enforcing，收集 `/dev/snd`、PCM、mixer、I2C、DSP和参数文件的实际 AVC 拒绝，建立专用守护进程域或等价受限特权域。
4. 只授予代理所需的目录搜索、字符设备 open/read/write/ioctl 和具体配置访问；禁止给整个 `untrusted_app` 域开放声卡。
5. SELinux Permissive 只允许在断开非必要网络、限定时间且有恢复守护的诊断中使用，不能进入生产镜像。
6. 补丁 boot 不足时，依次评估定制 recovery/system、特权系统服务和最小原厂服务桥。最后才评估保留原厂内核、DTB、HAL、DSP及校准的实验系统；通用 Linux 不得先于原厂 Android 路线覆盖 eMMC。

## R2：特权原厂音频代理

公开实现一个自有的最小特权守护进程。它从当前设备动态加载原厂库，不把专有二进制打包进 APK 或仓库，并完成：

- 按实机逆向和调用证据复现四麦 PCM、MicArray、DOA、AEC参考、增益、DSP和I2C的初始化/释放顺序。
- 管理原厂服务、AudioFlinger和代理之间的音频所有权；任何时刻只允许一个底层采集所有者。
- 接收所有 R1 本地播放源的参考，包括提示音、TTS、媒体和蓝牙；无法取得参考的来源必须明确报告，不能宣称受 AEC 保护。
- 通过本地 Unix socket 向卫星 APK 提供版本协商、启动、停止、健康状态、DOA、播放参考和 PCM 帧。Socket 使用文件权限及 `SO_PEERCRED` 校验目标 UID，不开放网络端口。
- 对外生产音频固定为 PCM S16LE、16 kHz、单声道、20 ms/帧；代理内部可保留原厂通道数和采样率，但转换原因、算法和延迟必须记录。
- 崩溃时释放声卡、清除悬挂会话并由有界看门狗恢复；失败不得静默切换成标准 AudioRecord 并继续报告“原厂处理”。

公开仓库只提交自有代理、IPC协议、构建脚本、设备侧提取和哈希校验工具。原厂库、APK、固件、校准、完整镜像和修改镜像保留在本地；公开测试使用接口替身和合成音频。对逆向得到的接口、来源和许可证边界保留审计记录。

## R3：对照与验收

所有结论区分接口存在、模拟通过和 R1 真机通过。至少比较三条链路：原厂特权处理链、标准 AudioRecord 原始链、当前自研增强链，并保持房间、距离、播放内容、音量和说话材料一致。

- 分别刺激各麦克风和四个方向，证明真实通道响应、DOA变化和阵列处理生效；只返回成功码不能通过。
- 验证安静、家庭背景、提示音、TTS、媒体 60%/90%音量下的播放残留、真人语音保留、AEC、Alexa唤醒和自由插话。
- 沿用技术方案第14章：1米语音相对静音至少提高10 dB；正常环境唤醒率至少95%；音乐60%/90%音量唤醒率至少90%/85%；TTS插话到旧音频静音P95不超过500 ms；按键/停止指令到静音不超过300 ms。
- 记录丢帧、削波、参考延迟、处理耗时、CPU、PSS、温度和重启。先完成20秒、30分钟和24小时音频运行，最终候选再执行统一语音回归、网络恢复及72小时稳定性验收。
- 每种系统修改验证失败启动、看门狗及当前可达的回退路径；恢复后关键分区及音频文件哈希必须与对应基线一致。完整回刷仍按R0独立记录，不把免拆风险接受写成通过，也不故意破坏全部引导组件。
- 继续使用现有 Alexa 预训练模型，不恢复 KWS 训练或选型；只验证固定模型在原厂音频链上的真实效果。

首台通过后才向 3～8 台扩展。每台设备必须单独核对固件、校准、镜像和回刷能力，不直接写入首台完整镜像。

## 降级判定

下列路线必须全部实际执行并形成可复现证据，才能提出降级：

1. 临时或补丁 root 加专用代理；
2. 定制 SELinux 域和最小设备权限；
3. 定制 boot/recovery/system 环境；
4. 原厂私有库直接代理；
5. 最小原厂语音服务桥接；
6. 保留原厂内核、HAL、DSP和校准的实验系统路线。

只有无法稳定初始化/采集、无法取得播放参考、无法安全隔离权限、无法达到第14章硬性指标，或无法满足公开发布边界，才算路线失败。复杂、耗时、需要Root或需要已授权的boot/system/recovery刷写均不算失败理由；拆机不属于当前首台路线。全部免拆原厂路线达到该门槛后，先提交完整证据、风险和可达到的降级效果，由用户明确决定；不得自动切换到自研处理。
