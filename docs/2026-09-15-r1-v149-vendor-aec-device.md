# R1 v149原厂AEC离线实机验证

日期：2026-09-15

设备：`r1-sample01`，固件3448 / API 22 / SELinux Enforcing。

> 2026-09-16 复核发现本阶段设备摆放时麦克风朝下。本报告中的方向、距离、AEC/DOA、KWS分数和声学结论保留为历史证据，但受姿态影响，须在麦克风朝上的正确姿态下重新真机验收；不得直接继承为当前最终结论。

## 结论

已确认并实际调用设备 `/system/lib/libaec.so`，但本轮没有取得可交付的播放中
Alexa立即打断输入。原厂AEC能处理同窗口硬件参考且保持完整时长，然而既有Alexa
模型的最佳真人分数仍只有54/255，低于固定229门槛；4×及8×增益发生削波并使区分
变差。因此生产取消仍固定关闭，不能降低阈值或恢复播放期VAD停播。

## ABI与安全边界

离线DEX和ELF/DWARF共同确认原厂调用为`AEC(16000, 1)`，按顺序设置
`(0,600)`、`(2,1)`、`(3,0)`并以1200字节块处理。3448实机对三个选项分别返回
`0/-1/0`；原调用者同样忽略返回值。结构体字段及反汇编确认格式0的首输入为
`[mic, echo]`交织数据，第二个`process`参数为null。

APK仅声明相同Java JNI ABI并从系统加载`libaec.so`，没有打包或发布原厂库。诊断接收器
受`android.permission.DUMP`保护，运行在独立`:vendor_aec_probe`进程，只接受应用诊断
目录内、最长60秒的严格PCM S16LE/16 kHz/单声道WAV；输出大小有界。该入口不被生产
录音调用，native失败不会直接带走卫星主进程。

## 真机结果

- v146首次成功加载系统库，但探针因自行要求选项2返回0而失败；v147按原厂语义只记录
  `-1`并继续，单声道错误布局输出恰为输入一半，进程没有崩溃。
- v148使用错误的`[echo,mic]`顺序后恢复完整16.992秒输出，但静默/真人分数为82/54，
  反向结果与字段语义一致，未进入生产。
- v149改为`[mic,echo]`。软件播放参考加MicArray ASR输入得到静默8、真人39。
- 同次MicArray旁路导出的4路原始麦克风与2路硬件echo reference组成16组矩阵，全部
  输出字节与各自输入相同，单次约0.52～0.54秒。静默八组为2～8，真人八组为
  5、6、8、8、17、5、20、12；最佳组合仍只有20。
- 对最佳两组做2×/4×/8×固定增益：2×时两路最佳真人均54，对应静默20/24；4×及
  8×最高不超过33/24且已有满幅样本，不能通过继续放大达到229门槛。

采集窗口均为850帧，MicArray调用1061/1062次，序列缺口、丢帧、非法形状、异常生产
线程和队列满均为0；raw4mic、echo2ref、ASR和VAD负载均非空。20%配置对应真实音乐
索引3/15，原MicArray主输出已经出现满幅样本，所以音量不是可继续上调的安全修复项。

原始及派生诊断音频只保存在仓库外的私有目录。设备上的27个输入/增益文件和42个
原厂AEC输出/元数据已按固定前缀逐项枚举、删除并复核为空，不提交家庭录音。
